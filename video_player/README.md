# ESP32-S3 SD-Card Video Player — Waveshare ESP32-S3-LCD-2

Continuous-loop MJPEG video player for the Waveshare ESP32-S3-LCD-2, built
as a proper ESP-IDF project for VS Code. Video is stored as an MJPEG/AVI
file on a microSD card and streamed frame-by-frame to the onboard ST7789
LCD.

---

## 1. Hardware analysis

Both attached Waveshare examples were inspected directly (not assumed from
generic documentation). Every pin below is copy-pasted from their source,
not guessed.

**Critical finding — shared SPI bus:** the LCD and the SD card use
*identical* SCLK/MOSI/MISO pins (39/38/40) and only differ in their CS
pin (LCD=45, SD=41). This is a genuine shared-bus design, confirmed by
both example files independently using the same three pin numbers. The
project therefore calls `spi_bus_initialize(SPI2_HOST, ...)` **exactly
once** (in `lcd_driver_init()`), and the SD card driver attaches its own
SPI device to that already-initialized bus instead of re-initializing it
— this is the officially supported pattern for sharing one SPI bus
between an LCD and an SD card, and avoids the bus-conflict the task
description specifically asked to watch for.

**ESP-IDF version note (stated explicitly rather than guessed):** the
06_lvgl_example's `sdkconfig.defaults` header comment says it was
generated by *"ESP-IDF 5.1.4"*, but its `dependencies.lock` file (created
by the component manager at a later build) records `idf: version: 6.0.2`.
These two files disagree about which exact toolchain version was last
used. This project targets **ESP-IDF v5.1.x (LTS)** as the safe common
denominator — every API used here (`esp_lcd_panel_*`, `spi_master`,
`ledc`, `esp_vfs_fat_sdspi_mount`, `nvs_flash`) is stable and unchanged
across IDF 5.1 through 6.0, so it will build correctly on any IDF version
from 5.1 up. If you specifically need to match one of the two examples'
exact toolchain, install that version's `idf.py` and it will still work
unmodified.

LVGL itself is **not used** by this project — see §4 for why.

## 2. Recommended video format

**Can the ESP32-S3 decode H.264 MP4 in real time? No.** The ESP32-S3 has
no hardware video decoder of any kind — no H.264, no H.265. Its only
video/image-adjacent silicon is the LCD_CAM peripheral (for driving
parallel-RGB or I8080 displays, not decoding), which this board doesn't
even use (it drives the LCD over SPI). Software-decoding a real H.264
stream at any usable frame rate on a 240 MHz Xtensa core is not
realistic for a full-screen video player.

**What the ESP32-S3 *can* do well:** decode baseline JPEG images quickly
in software, and even better than most competing chips, because the
ESP32-S3 has SIMD (Xtensa "PIE") instructions that JPEG codecs can use.
Espressif's own `esp_new_jpeg` component (used by this project) is
specifically optimized for this.

**Recommendation: Motion-JPEG (MJPEG) video inside an AVI container.**
Each frame is an independent JPEG image — there's no inter-frame
prediction to worry about, no B/P-frame reordering, no reference-frame
management, and a corrupt/truncated frame only affects that one frame
(a real robustness advantage on removable SD media). This is exactly the
format most ESP32-CAM-class projects converge on for the same reasons.

| Setting     | Recommendation | Why |
|-------------|----------------|-----|
| Resolution  | **240 x 320** (match the LCD exactly) | Avoids needing a scaler on-device; scaling JPEG output in software would cost CPU budget better spent on decode throughput. |
| Frame rate  | **10–12 fps** | At 240x320, this is a realistic sustained rate for SPI transfer (80 MHz, RGB565 = 153,600 bytes/frame) plus software JPEG decode plus SD read, with headroom left over. Higher is possible with a very fast card and low quality, but 10-12 fps is a safe target. |
| Codec       | MJPEG (`-c:v mjpeg`) | Only realistic option without hardware video decode — see above. |
| Container   | AVI | Simplest MJPEG container to parse without pulling in a general demuxer library; ffmpeg's default `.avi` MJPEG output matches exactly what `avi_reader.c` in this project parses. |
| Quality     | `-q:v 6` (ffmpeg's 2–31 scale, lower = better) | Balances visible quality against frame size / decode time. Increase (worse quality, e.g. 10-12) if you need higher fps or hit the frame-size limit; decrease (better quality, e.g. 3-4) if you have SD/decode headroom to spare. |
| Audio       | **None.** | This board's example projects show no I2S/DAC audio hardware, and the task is explicitly video-only. Audio is not implemented; strip it in the ffmpeg command below. |

## 3. FFmpeg conversion command

```bash
ffmpeg -i input.mp4 \
  -vf "scale=240:320:force_original_aspect_ratio=decrease,pad=240:320:(ow-iw)/2:(oh-ih)/2,fps=12" \
  -c:v mjpeg -q:v 6 -an \
  video.avi
```

- `scale=...:force_original_aspect_ratio=decrease` + `pad=...` letterboxes
  or pillarboxes the source into exactly 240x320 without distortion,
  regardless of the input's original aspect ratio.
- `fps=12` resamples to the recommended frame rate.
- `-an` strips audio (see above).
- Copy the resulting `video.avi` to the root of the SD card and make sure
  `board_config.h`'s `VIDEO_FILE_PATH` matches its name/location
  (defaults to `/sdcard/video.avi`).

If frames come out larger than `VIDEO_MAX_JPEG_FRAME_SIZE` (96 KB, in
`video_player.h`) — very unlikely at 240x320/q6, but possible with a
very high-detail/high-motion source — raise `-q:v` (worse quality) or
raise that constant.

## 4. Project architecture

```
SD Card (microSD, SPI, shared bus)
   |
   |  avi_reader.c: parses RIFF/AVI, walks the 'movi' chunk list,
   |  reads one "00dc" chunk (one JPEG frame) at a time
   v
reader_task (core 0)
   |  hands the compressed JPEG bytes to...
   v
FreeRTOS queue (3 buffers, pool-based, no heap churn)
   v
decoder_task (core 1)
   |  jpeg_decoder.c: espressif/esp_new_jpeg decodes JPEG -> RGB565
   |  directly into one of two PSRAM framebuffers (double-buffered)
   v
lcd_driver.c: esp_lcd_panel_draw_bitmap() -> SPI + DMA -> ST7789 LCD
```

**Why not LVGL for the video path:** LVGL is a retained-mode UI toolkit —
its value is managing a tree of widgets, dirty-rectangle partial redraws,
input events, and styling. A full-screen video player redraws all
240x320 pixels every single frame; there are no widgets, no partial
redraws, nothing for LVGL's object model to do except add a buffer
copy and its own task/refresh-timer overhead on top of what
`esp_lcd_panel_draw_bitmap()` already does directly. This project talks
to the exact same `esp_lcd_panel_*` driver the LVGL example installs,
just without LVGL in between — this is a deliberate architecture choice
per the task's own guidance to prioritize smooth playback over reusing
LVGL just because the reference example happened to use it.

**Double buffering / task split rationale:** the reader task and decoder
task run pinned to different cores specifically so that SD-card I/O
(which blocks on SPI transactions) never stalls JPEG decoding, and so
that JPEG decoding (CPU-bound) never stalls the LCD DMA handoff. The two
RGB565 framebuffers let the decoder start decoding the *next* frame into
buffer B while the *previous* frame (buffer A) is still being clocked out
to the LCD over SPI/DMA — `lcd_driver_draw_fullscreen()` only blocks long
enough to guarantee the buffer it's about to hand to DMA isn't currently
in flight.

**Memory placement:** both RGB565 framebuffers (~150 KB each) and all
three compressed-frame buffers (96 KB each) are allocated from PSRAM via
`MALLOC_CAP_SPIRAM` — exactly like the reference LVGL example allocates
its own draw buffers — because the ESP32-S3's GDMA controller can DMA
directly out of PSRAM, and internal SRAM is far too small (and needed by
FreeRTOS/WiFi-adjacent system tasks) to hold buffers this size. Small,
short-lived buffers (a single LCD row for status screens) use internal
DMA-capable RAM instead, since they're tiny and not on the hot path.

## 6. Installation / setup

1. **Create the project.** Copy this entire `video_player/` folder
   somewhere on disk, e.g. `~/esp/video_player`.
2. **Open in VS Code** with the Espressif IDF extension installed, via
   *File → Open Folder* on `video_player/`.
3. **Select the target:**
   ```bash
   idf.py set-target esp32s3
   ```
   (or via the VS Code IDF extension's target picker — pick `esp32s3`).
4. **Install dependencies.** The first build automatically fetches
   `espressif/esp_new_jpeg` via the IDF Component Manager using
   `main/idf_component.yml` — no manual step needed, as long as the
   machine has internet access during the build.
5. **(Optional) Configure:** `idf.py menuconfig` if you want to change
   anything beyond what's in `sdkconfig.defaults` (log level, watchdog
   timeout, etc).
6. **Build:**
   ```bash
   idf.py build
   ```
7. **Flash:**
   ```bash
   idf.py -p <PORT> flash
   ```
8. **Open the serial monitor:**
   ```bash
   idf.py -p <PORT> monitor
   ```
9. **Prepare the SD card:** format it FAT32 (standard for cards up to
   32 GB; use exFAT/third-party tools for larger cards plus IDF's exFAT
   support if needed — not covered by this project's default FAT
   configuration).
10. **Convert and copy the video:** run the ffmpeg command from §3, then
    copy the resulting `video.avi` to the root of the SD card.
11. **Insert the card and power/reset the board.** Playback starts
    automatically and loops continuously.

## 7. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| SD card not detected (`SD CARD ERROR` on screen) | Check wiring against §1's pin table (MOSI=38, MISO=40, CLK=39, CS=41). Confirm pull-up resistors are present on the SD lines (per the original example's own note). Try a different, known-good card. |
| LCD stays white/black at boot | LCD init failed before it could even show an error (this is the one failure mode that's serial-log-only — check the monitor). Re-check LCD pins (SCLK=39, MOSI=38, DC=42, CS=45) and that backlight GPIO1 is actually wired. |
| Colors look wrong / inverted | This ST7789 needs `esp_lcd_panel_invert_color(true)`, which is already set in `lcd_driver.c` to match the reference example. If you swap panels, this may need to change. |
| Image is mirrored / rotated wrong | Adjust `LCD_MIRROR_X` / `LCD_MIRROR_Y` / `LCD_SWAP_XY` in `board_config.h`. The defaults match the reference LVGL example exactly. |
| `FILE NOT FOUND` on screen | Confirm the file is literally at `/video.avi` on the card's root (or update `VIDEO_FILE_PATH` in `board_config.h` to match), and that the card mounted successfully (check the monitor log line "SD card mounted" and the file listing from `sdmmc_card_print_info`). |
| "Video is WxH but the LCD is 240x320" warning, then decode errors | Your source wasn't (re-)encoded to exactly 240x320. Re-run the ffmpeg command in §3 — don't skip the `scale`/`pad` filters. |
| Video does not decode / `UNSUPPORTED FORMAT` at boot | The file isn't valid RIFF/AVI, or doesn't contain a `movi` list this minimal parser recognizes (see the comment at the top of `avi_reader.c` for exactly what's supported). Re-encode with the exact ffmpeg command given. |
| Playback is slow / low, uneven frame rate | First check the monitor for repeated "Dropped a frame" or "SD read error" warnings. Try lowering resolution isn't an option (must match LCD), so instead: lower fps in the ffmpeg command, raise `-q:v` (smaller/faster-to-decode frames), or use a faster SD card (Class 10 / U1 or better). |
| Frequent dropped frames only under sustained playback | Possible SD card write endurance/quality issue, or a marginal card that's slow on random small reads — try a different card, or increase `SHARED_SPI_MAX_TRANSFER_SZ` in `board_config.h` if you're using very large single reads elsewhere. |
| Insufficient memory / boot halts with `MEMORY ERROR` | Confirm PSRAM is actually detected: check the monitor boot log for a PSRAM size line. If PSRAM shows as 0 or missing, re-check `sdkconfig.defaults`' `CONFIG_SPIRAM*` lines survived your `idf.py menuconfig` changes (menuconfig can silently unset these if you touch that submenu). |
| PSRAM not found / boot loop mentioning PSRAM | Confirm your specific board revision actually has the Octal PSRAM part (`CONFIG_SPIRAM_CLK_IO=30` / `CS_IO=26`, from the reference example) — a Quad-PSRAM revision of this board would need different `CONFIG_SPIRAM_MODE_*` settings; this isn't something the two attached examples can disambiguate for every board revision, so check yours against Waveshare's product page if this shows up. |
| SPI bus conflict / one peripheral works but not both together | Make sure you haven't added a second `spi_bus_initialize(SPI2_HOST, ...)` call anywhere — `lcd_driver_init()` must be the only one, and it must run before `sd_storage_init()`. This is enforced by the call order in `main.c`; don't reorder it. |

## Design decisions worth knowing about

- **On-screen error text** uses a tiny hand-built 5x7 bitmap font
  (`simple_font.c`), not LVGL or any font-rendering library, to avoid
  pulling in exactly the overhead this project avoids for the sake of a
  handful of boot-time status strings. It only supports uppercase
  letters, digits, space, and `. : / -` — enough for the short status
  messages this app shows. Full diagnostic detail always goes to the
  serial monitor via `ESP_LOG*`.
- **NVS is initialized** even though nothing in this app currently reads
  or writes it, per the requirement to initialize it "if required" —
  it's cheap, and several ESP-IDF subsystems probe it at init and warn
  if it's missing. Remove the `nvs_flash_init()` call in `main.c` if you
  want to trim it.
